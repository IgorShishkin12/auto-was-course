Reading gorilla/securecookie sessions

Several challenges on this course run the same Go/Echo + gorilla/sessions skeleton, so it is worth knowing the cookie format cold.

Wire format

SecureCookie.Encode (v1.1.x) does:

b = encode(gob_serialize(value))                    // base64url of the gob bytes
b = fmt.Sprintf("%s|%d|%s|", name, timestamp, b)    // "session|1795226492|DX8E...|"
mac = HMAC(hashKey, "session|1795226492|DX8E...")   // note: without the trailing '|'
b = append(b, mac...)[len(name)+1:]                 // drop "session|"
cookie = base64url(b)                               // "1795226492|DX8E...|<32 bytes>"

So after one base64 decode you get three pipe-separated fields: timestamp | payload | MAC. The payload is itself base64url of a gob-encoded map — readable with a plain base64 -d:

\x0f\x7f\x02\x01\x0c\x02\x01\x04\x01\x00\x04\x01\x00*\xff\x80\x00\x01\x04\x01\x06\x03\x04\x04\x08\x02
\tstring\x0c\x07\x00\x05login\x06string\x0c\x0d\x00\x0bsomenewuser

That is why "client-side session" challenges are so often solvable: the state is visible, only the integrity tag stands between you and a forged login=admin.

What the tag protects

mac = HMAC-SHA256(hashKey, name|timestamp|payload). There is no encryption unless a block key was supplied (NewCookieStore called with two keys). Consequences:

  • When sessions are signed but not encrypted, never put secrets in them — anyone can read them.
  • The timestamp is inside the MAC scope: decode also enforces MaxAge, so you cannot "refresh" an old cookie without the key.
  • If the key is a file read at boot (e.g. secret.txt), the whole scheme reduces to file permissions.

Attacking the key

Two honest options:

  1. Guess it. If the app derives hashKey from a word, you can verify candidates offline in microseconds — no requests to the server needed:
ts, payload, mac = base64.urlsafe_b64decode(cookie + "==").split(b"|")
msg = b"session|" + ts + b"|" + payload
hmac.new(candidate, msg, sha256).digest() == mac[:32]

I ran the full rockyou list (14.3 M candidates) against a live cookie at ~345 k/s; nothing. A random 32-character key survives this trivially.

  1. Find a different flaw. If the key is random, stop attacking the MAC and attack the app: password reset, IDOR, mass assignment, CSRF against a privileged bot, or a second app that shares the key.

Practical checklist for this family

# decode any session cookie you are given
python3 - <<'PY'
import base64,sys
raw=sys.argv[1]; d=base64.urlsafe_b64decode(raw+"="*(-len(raw)%4))
print(d.split(b"|")[0], d.split(b"|")[1], d.split(b"|")[2].hex())
PY
  • If the payload ends in readable gob/JSON → signed-only cookie.
  • If the three fields are missing → a different scheme (itsdangerous, JWT, custom).
